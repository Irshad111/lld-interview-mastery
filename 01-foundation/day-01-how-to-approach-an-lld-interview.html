Day 1 — How to Approach an LLD Interview

Practice problem: Library Management System

Goal: Learn how to turn a problem into a clear, simple design before writing code.

Main lesson: Start with the requirements, not with code or design patterns. Build only what the problem needs.

1. What Is LLD?

LLD means Low-Level Design. It is planning the parts inside a program: which classes we need, what each class is responsible for, and how those classes work together.

For example, a library program may need to represent a book title, a physical copy, a member, and a borrowing record.

2. A Simple Interview Plan

  1. Understand what the system must do.
  2. Identify who will use it.
  3. List the main actions they need.
  4. Choose the important objects the program must remember.
  5. Decide what each object should know and do.
  6. Decide how the objects connect.
  7. Write the main code and check important cases.
  8. Explain what you would add if the requirements grew.
Requirements
    ↓
Users and actions
    ↓
Objects and responsibilities
    ↓
Connections between objects
    ↓
Code → Checks → Improvements

3. Understand the Problem First

The interviewer says: “Design a Library Management System.” This is broad, so first agree on a small set of requirements.

For today's version, the library must be able to:

  • Add a physical copy of a book.
  • Register a member.
  • Search for a book by title.
  • Lend an available copy.
  • Accept a returned copy.
  • Show whether a copy is available.

We will not build a website, database, login system, or distributed service today. We are focusing on the basic design inside the program.

4. Who Uses the System?

In design discussions, an actor means a person or another system that uses the system we are designing.

ActorActions
MemberSearch for a book, borrow a copy, return a copy.
LibrarianAdd book copies and register members.

5. Find the Important Objects

An object represents something in the program and can hold information about it. In Java, a class defines the structure used to create objects.

  • Book: information about a book title.
  • BookCopy: one physical copy owned by the library.
  • Member: a registered person.
  • Loan: a record that a member borrowed a particular copy.
  • Library: coordinates the main operations.

Do not turn every word in a requirement into a class. Create a class when it represents something important that the program needs to remember or act on.

6. Why Separate Book and BookCopy?

Imagine the library owns three copies of Clean Code.

Book: "Clean Code"
  ├── Copy C-101 — available
  ├── Copy C-102 — borrowed
  └── Copy C-103 — available

Book holds details shared by all copies, such as title and author. BookCopy represents one real copy. Each copy has its own ID and availability.

If availability were stored only on Book, we would not know which of the three copies had been borrowed.

7. Give Each Object a Responsibility

Ask: “What information should this object hold, and what action should it control?”

ClassInformationResponsibility
BookISBN, title, authorProvide book details.
BookCopyCopy ID, book, availabilityAllow borrowing and returning.
MemberMember ID, nameRepresent a registered member.
LoanMember, copy, borrow time, return timeRecord a borrowing.
LibraryCopies, members, loansCoordinate library operations.

8. Let an Object Protect Its Own Information

We must prevent a second borrow attempt when a copy is already borrowed. Instead of letting any code change availability directly, let BookCopy check its state first.

public void borrow() {
    if (!available) {
        throw new IllegalStateException("Copy is not available");
    }
    available = false;
}

This is called encapsulation: an object keeps control over its information and the rules for changing it.

9. How the Objects Connect

Library
 ├── keeps track of BookCopy objects
 ├── keeps track of Member objects
 └── keeps track of Loan objects

BookCopy ── represents one physical copy of ──> Book
Loan ── records which Member borrowed which BookCopy

The Library coordinates the operation, but BookCopy checks whether it can be borrowed.

10. Java Implementation

The runnable implementation is maintained in src/main/java/com/lld/library/. Use those files as the source of truth for the current implementation.

Put each public class in a separate file under package com.lld.library.

Book.java

package com.lld.library;

public class Book {
    private final String isbn;
    private final String title;
    private final String author;

    public Book(String isbn, String title, String author) {
        this.isbn = isbn;
        this.title = title;
        this.author = author;
    }

    public String getIsbn() { return isbn; }
    public String getTitle() { return title; }
    public String getAuthor() { return author; }
}

BookCopy.java

package com.lld.library;

public class BookCopy {
    private final String id;
    private final Book book;
    private boolean available = true;

    public BookCopy(String id, Book book) {
        this.id = id;
        this.book = book;
    }

    public void borrow() {
        if (!available) {
            throw new IllegalStateException("Copy is not available");
        }
        available = false;
    }

    public void returnBook() {
        if (available) {
            throw new IllegalStateException("Copy has not been borrowed");
        }
        available = true;
    }

    public String getId() { return id; }
    public Book getBook() { return book; }
    public boolean isAvailable() { return available; }
}

Member.java

package com.lld.library;

public class Member {
    private final String id;
    private final String name;

    public Member(String id, String name) {
        this.id = id;
        this.name = name;
    }

    public String getId() { return id; }
    public String getName() { return name; }
}

Loan.java

package com.lld.library;

import java.time.LocalDateTime;

public class Loan {
    private final Member member;
    private final BookCopy bookCopy;
    private final LocalDateTime borrowedAt;
    private LocalDateTime returnedAt;

    public Loan(Member member, BookCopy bookCopy) {
        this.member = member;
        this.bookCopy = bookCopy;
        this.borrowedAt = LocalDateTime.now();
    }

    public void returnBook() {
        if (!isActive()) {
            throw new IllegalStateException("Loan has already been returned");
        }
        bookCopy.returnBook();
        returnedAt = LocalDateTime.now();
    }

    public boolean isActive() { return returnedAt == null; }
    public Member getMember() { return member; }
    public BookCopy getBookCopy() { return bookCopy; }
    public LocalDateTime getBorrowedAt() { return borrowedAt; }
    public LocalDateTime getReturnedAt() { return returnedAt; }
}

Library.java

package com.lld.library;

import java.util.ArrayList;
import java.util.List;

public class Library {
    private final List<BookCopy> copies = new ArrayList<>();
    private final List<Member> members = new ArrayList<>();
    private final List<Loan> loans = new ArrayList<>();

    public void addBookCopy(BookCopy copy) {
        copies.add(copy);
    }

    public void registerMember(Member member) {
        members.add(member);
    }

    public List<BookCopy> searchByTitle(String title) {
        List<BookCopy> matches = new ArrayList<>();
        for (BookCopy copy : copies) {
            if (copy.getBook().getTitle().equalsIgnoreCase(title)) {
                matches.add(copy);
            }
        }
        return matches;
    }

    public Loan borrowBook(Member member, BookCopy copy) {
        if (!members.contains(member)) {
            throw new IllegalArgumentException("Member is not registered");
        }
        if (!copies.contains(copy)) {
            throw new IllegalArgumentException("Copy does not belong to this library");
        }
        copy.borrow();
        Loan loan = new Loan(member, copy);
        loans.add(loan);
        return loan;
    }

    public void returnBook(Loan loan) {
        if (!loans.contains(loan)) {
            throw new IllegalArgumentException("Loan does not belong to this library");
        }
        loan.returnBook();
    }
}

11. Walk Through One Example

  1. The library registers member M-1.
  2. The library adds copy C-101 of Clean Code.
  3. The member asks to borrow C-101.
  4. The library checks that the member and copy belong to this library.
  5. BookCopy checks availability and marks the copy as borrowed.
  6. The library creates a Loan to record who borrowed the copy.
  7. When the loan is returned, the copy becomes available again.

12. Important Cases to Check

  • Borrowing an available copy succeeds.
  • Borrowing the same copy twice fails.
  • Returning a borrowed copy makes it available.
  • Returning the same loan twice fails.
  • An unregistered member cannot borrow.
  • A copy outside this library cannot be borrowed through it.

We will learn JUnit separately, so you do not need to master test syntax today. Focus on deciding what should work and what should be rejected.

13. Why We Are Not Adding Design Patterns Yet

A design pattern is a commonly used way to solve a recurring design problem. It is a tool, not a requirement for every program.

If a requirement says…Consider…
There are several ways to calculate a late fee.A Strategy-style design, because the calculation can vary.
There are several ways to create different notification types.A Factory, if the program must choose how to create an object by type.
Books must be saved in a database.A separate storage/repository layer.
Two people might borrow the same copy at the same time.Concurrency protection, which we will study later.

The current requirements can be handled with a few straightforward classes. Adding patterns now would make the design harder to follow without solving a real problem.

14. Interview Follow-up Questions

Q1. A member can borrow at most five copies. Where would you enforce this?

Check the member's current active loans and limit before creating a new loan. As the rules grow, a separate borrowing policy may help keep them together.

Q2. Different membership types have different limits. What might change?

The limit varies by membership type. Keep this rule in one place instead of spreading membership checks through the code.

Q3. What if the library has thousands of copies?

The in-memory list is fine for learning. A real application may need database storage and faster searching, which are later improvements.

Q4. What if two members try to borrow the same copy at nearly the same time?

Both operations could check availability before either updates it. A real system needs a safe way to claim the copy. We will study this later.

15. Common Mistakes

  • Writing code before agreeing on requirements.
  • Making every noun a class without checking whether it is useful.
  • Putting all rules into one giant class.
  • Adding patterns just to make the design look advanced.
  • Forgetting invalid cases, such as borrowing an unavailable copy.
  • Confusing a book title with one physical copy.

16. How to Explain Your Design in an Interview

“First, I clarified the actions the library must support. I identified the member and librarian as the users. I separated Book from BookCopy because one title can have several physical copies, each with its own availability. Loan records who borrowed which copy. Library coordinates the operations, while BookCopy protects its availability rule. I kept the design simple because the current requirements do not need extra patterns.”
